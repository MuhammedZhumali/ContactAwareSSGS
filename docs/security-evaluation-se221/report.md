# SE2.2.1: надёжность checkpoint и ограниченное ускорение X

Ограниченный этап выполнен: **12 новых попыток — 7 FINISHED и 5
CONTROLLER_TIME_LIMIT**. Ошибок процесса в новой серии нет. Представительный
поиск Multi CONTINUE_WAIT при t=0 теперь завершён, но полные контроллеры с этим
правилом исчерпывают общий бюджет в начале C1. Поэтому сравнение поздних атак X
при обоих правилах остаётся незавершённым. Остановка не считается проигрышем политики.

[Таблица всех 12 повторов](retry-table.md) связывает исходные и новые журналы.
[CSV](tables/twelve-retries.csv), [полная объединённая таблица](tables/combined-comparisons.csv)
и [проверки](validation.json) содержат машинно читаемые результаты.

## Checkpoint: что установлено и исправлено

Во всех семи прежних ошибках `AccessDeniedException` возникал при атомарном
переименовании временного checkpoint. Сохранились читаемые прежний checkpoint
и `.tmp`. Источник запрета Windows — процесс, фильтр, условие доступа или другая
причина — **не установлен**. Название блокирующей программы из журналов не следует.

Теперь сериализация идёт в уникальный соседний temp. Старый checkpoint не
обрезается и не удаляется. Повторяется только AccessDenied: максимум четыре
попытки, пауза 25 ms, окно повторов 250 ms от первого переименования. После
паузы срок проверяется снова. Постоянный отказ завершает запись явным
`WriteFailure`, сохраняет старый файл и диагностический temp; harness сообщает
`CHECKPOINT_WRITE_FAILED`. Остальные I/O-ошибки не маскируются повторами.
Неподдерживаемая атомарная замена теперь завершается отказом: небезопасного
неатомарного fallback нет. [Подробный контракт](checkpoint-notes.md).

`WriteDiagnostics` содержит число попыток/повторов, AccessDenied, backoff,
полное время записи, время стадии переименования и длительность каждой попытки.
Сериализация учитывается в полном времени, но не в 250 ms окне переименования.
Кооперативный срок не может прервать уже выполняющийся системный вызов или сон;
внешний watchdog остаётся отдельной защитой. Гарантия не распространяется на
аварийное отключение питания и аппаратную целостность файловой системы.

Проверки через внедрённые mover/clock/sleeper прошли:

| Управляемый случай | Проверенный результат |
|---|---|
| Два отказа, затем успешная замена | 3 попытки, 50 ms backoff, 53 ms полного времени; старые байты до успеха неизменны |
| Постоянный отказ | 4 попытки, 75 ms backoff; старый checkpoint побайтово сохранён и восстанавливается |
| Долгое переименование / позднее пробуждение | После истечения окна новая попытка не начинается |
| Долгая сериализация | Не съедает окно повторов переименования, входит в полное время |
| Atomic move unsupported / другая I/O-ошибка | Явный отказ без небезопасного fallback или лишних повторов |
| Ошибка сериализации | Ноль переименований, предыдущий checkpoint сохранён |
| Прерывание во время backoff | Флаг прерывания и прежний файл сохранены |

Тест восстановления содержит начатую операцию: восстановленное исполнение даёт
те же состояние и результат, что непрерывное. Четыре прежних теста дополнительно
покрывают кадры в полёте, уведомления и бюджет контроллера. Логи:
[13 focused tests](../../target/security-evaluation-se221/checkpoint-tests.log),
[чистая сборка A](../../target/security-evaluation-se221/build-a.log).

Все семь повторов A завершились. Выполнено **1005 записей checkpoint без отказов**;
на всех 12 новых попытках — **1047 записей, 0 повторов**, суммарно 6.986 s,
максимум одной записи 0.231 s. Это измерения полного времени, а не только rename.
[Все записи](tables/checkpoint-writes.csv). Значит, прежняя блокировка не
воспроизвелась; нельзя приписывать успех повторов срабатыванию backoff.
Его поведение доказывают контролируемые тесты. Все 12 финальных checkpoint
сверены с фактическим временем, security state и полным журналом: совпадение.

## Один вход для пяти проблемных поисков

`Se221ObservationAudit` прочитал сохранённые checkpoint и спроецировал
`PlanningObservation` с H=2. Сравнены **все сериализованные поля**, а не только
время или видимые контакты. Все пять наблюдений при t=0, decision index 1,
эквивалентны. Граница сверена с исходным последним незавершённым решением;
предыдущие поиски не повторялись. Будущая скрытая атака не попадает в наблюдение.
[Исходник проверки](Se221ObservationAudit.java),
[результат](../../target/security-evaluation-se221/observations/equivalence.json).

Выбран единственный представитель `X-multi-none-continue_wait`.
Оба новых диагностических поиска использовали JAR B и тот же вход; различался
только traversal. [Полные результаты и планы](tables/representative-search.json).

| Показатель | RENEWAL_FIRST | SERVICE_FIRST |
|---|---:|---:|
| Статус | INCOMPLETE / TIME_LIMIT | COMPLETE |
| Узлы | 286413 | 134638 |
| Elapsed, s | 30.001 | 11.601 |
| CPU потока поиска, s | 29.094 | 11.000 |
| Генерация, s | 5.248 | 2.432 |
| Исполнение ветвей, s | 6.298 | 3.153 |
| Оптимистическая граница, s | 10.352 | 2.632 |
| Ключ состояния, s | 4.072 | 1.563 |
| Терминальные планы | 270 | 16 |
| Memo hits / entries | 6080 / 396 | 0 / 23 |
| JVM GC delta, ms | 293 | 89 |
| Пятёрка результата | (3; 37 s; 0.83 s; 1240 B; 2) | (3; 37 s; 0.83 s; 1240 B; 2) |

Фазы взяты из `runtimeTelemetry.phaseElapsedNanos`; это частичный профиль,
есть прочие фазы и неатрибутированное время. GC delta относится ко всей JVM,
CPU потока не включает GC-потоки. Из этих данных не следует причина прежнего
интервала 3361 s; она остаётся неизвестной.

RENEWAL_FIRST исследует INSTALL и видимый PREPARE раньше CONTINUE. При
альтернативном итоговом правиле это быстро даёт хороший по пятёрке, но
не предпочтительный среди равных план. Префикс CONTINUE лучше раннего service,
и равная оптимистическая граница не позволяет отбросить его относительно такого
incumbent. Поиск постепенно находит всё более отложенные равноценные продолжения.
Недостаток ёмкости memo не подтверждён: capacity skips равны нулю. Поддеревья,
отсечённые относительно incumbent, не становятся доказанными оптимальными
суффиксами и не могут произвольно публиковаться в кэше.

Ограниченное изменение — `PlannerOptions.acceleratedServiceFirst()`:
CONTINUE, SWITCH, INSTALL, OPEN, REUSE, WAIT, PREPARE. Это **обход**, а не
итоговый порядок CONTINUE → WAIT → service. По умолчанию старый обход сохранён.
Генератор, comparator, канонические отсечения, точный memo и его ёмкость не
изменялись. Правило обхода применимо одинаково к Next/Multi и обоим tie-break.
[Разбор корректности](search-notes.md).

Пятёрка найденного ранее incumbent совпала с новым точным результатом, но
**полные планы различаются**. В незавершённом incumbent PREPARE был в 5.25 s,
INSTALL в 14.5 s; в COMPLETE плане — 13.75 s и 15.75 s. Оба плана имеют
164 действия и прошли повторное исполнение до единой границы. Прежний
INCOMPLETE не доказывал итогового победителя, поэтому совпадение с ним нельзя
использовать как проверку полного плана.

Такая проверка выполнена на двух нетривиальных малых задачах для обоих правил:
полный DFS, прежнее и новое ускоренное исполнение, обычный и обратный обход.
Во всех четырёх тестах совпали пять показателей, первое действие и **весь план**;
каждый план повторно исполнен. Одна задача требует полной цепочки создания
материала; другая имеет настоящее равенство INSTALL/CONTINUE с разными
победителями CANONICAL и CONTINUE_WAIT.

## Что всё ещё дорого в полном контроллере

Все пять повторов B прошли несколько COMPLETE решений, затем были остановлены
общим бюджетом. Последнее незавершённое решение не исполнено. Снимок сохранён,
финальные метрики не публикуются; watchdog не потребовался.

| X Multi alternative | COMPLETE / INCOMPLETE решений | Достигнуто t, s | Сумма поиска, s | Узлы | CPU контроллера, s |
|---|---:|---:|---:|---:|---:|
| none | 6 / 1 | 1.75 | 59.642 | 775534 | 58.125 |
| original | 6 / 1 | 1.75 | 59.763 | 784024 | 58.625 |
| p70 | 6 / 1 | 1.75 | 59.750 | 797108 | 58.344 |
| p90 | 7 / 1 | 2.00 | 59.733 | 819100 | 57.844 |
| gap-midpoint | 7 / 1 | 2.00 | 59.740 | 839010 | 57.688 |

Полное elapsed контроллеров — 60.002–60.004 s, GC delta 356–390 ms.
Разница достигнутого времени между пятью случаями не доказывает влияния скрытых
атак: меняется число успевших завершиться поисков при wall-clock ограничении.
Они остановились до атаки и уведомления НС; метрики восстановления здесь
**unavailable**, а не ноль и не измеренное медленное восстановление.
Частичный прогресс: 0 обслуженных контактов, 0.75–1 s полезной передачи,
0.06 s модельного control CPU, 80 служебных B, 0 новых ключей. Эти значения
не используются как финальный результат политики.
[Прогресс](tables/controller-progress.csv), [каждое решение/фазы](tables/search-decisions.csv).

Конкретный пример none: поиск OPEN при t=0 занял 11.630 s / 134638 узлов.
Начало OPEN создаёт выполняемую операцию при том же модельном времени;
следующий поиск WAIT до её конца снова занял 10.505 s / 134633 узла.
Затем CONTINUE в t=1, 1.25, 1.5 s заняли по 9.68–9.87 s и около 134.6 тыс.
узлов каждый. Это повторная работа над близкими продолжениями. `plan()` создаёт
новый `Search`, а memo принадлежит одному Search; между решениями он не
переиспользуется. Даже успешный корневой поиск не устраняет эту стоимость.

Внутри корневого SERVICE_FIRST остаются 542067 сгенерированных WAIT;
476352 действия WAIT исключены существующим доказанным правилом до исполнения,
65715 WAIT всё же исполнены. Исполнение ветвей, границы и генерация занимают
основную измеренную долю. Это конкретный оставшийся профиль, а не предположение
о внешней паузе компьютера. Дальнейшая оптимизация в этом этапе не проводилась.
Возможный следующий отдельный шаг — доказать безопасное использование уже
решённого продолжения между решениями, учитывая события, горизонт и полный
tie-break. Простое отключение решений после кадров изменило бы постановку.

## Поздние атаки X и исследовательский вывод

Определения атак и метрик SE2/SE2.1 сохранены. Четыре этапа восстановления:
подтверждение уведомления КА, независимая допустимая активная пара, открытая SA,
первый независимый доставленный кадр — остаются раздельными. Первое достижение
не означает непрерывную готовность; интервалы и последующие закрытия/expiry
сохранены в [readiness](tables/readiness-intervals.csv) и
[overlapping conditions](tables/overlapping-conditions.csv), без сложения
перекрывающихся причин. [Все новые этапы](tables/recovery-milestones.csv).

Новый завершённый p70 canonical подтверждает: Multi обслужил три контакта,
Next — два. У Multi после уведомления НС: notice 0.4 s, пара 1.4 s, SA 2.4 s,
кадр 2.65 s; у Next независимая пара/SA/кадр не наблюдались до конца опыта.
Цена Multi выше: (3; 35.5 s; 0.93 s; 1416 B; 2) против
(2; 34 s; 0.66 s; 1056 B; 2). Это преимущество по выбранным показателям,
а не по всем расходам.

|---|---:|---:|---:|---:|

Для Next первый независимый кадр во всех трёх строках цензурирован концом
эксперимента. p90/gap и Next p70 — прежние завершённые SE2.2 результаты;
новый здесь только Multi p70. Разница раскрытия в этих строках относится
к записанной истории **до** атаки; послераскрытый трафик одинаков.
Нельзя объявлять всю разницу раскрытия следствием скорости восстановления.

Для CONTINUE_WAIT завершены Next, но отсутствует завершённый Multi в каждом X.
Следовательно, **сохранение преимуществ поздних атак при обоих правилах не
установлено**. Корневой номинальный план без атаки не заменяет полный запуск
контроллера с перепланированием и аварийной реакцией. Прежний вывод ISS CP5400
о зависимости восстановления от tie-break не изменён и здесь заново не проверялся.

Пять завершённых canonical повторов совпали с SE2 по журналам и simulation/security
метрикам. Для трёх доступных завершённых original-X сочетаний сохранённый
Claude replay совпал по метрикам и всем действиям. Для Multi alternative такого
завершённого сравнения нет; прежний tied-child helper Claude не отбрасывал
все nonnull INCOMPLETE оценки и не используется как доказательство оптимальности.

## Проверки и ограничения свидетельств

Чистая сборка B: **374 теста, 0 ошибок/провалов/пропусков**.
[Лог Maven](../../target/security-evaluation-se221/build-b.log).
Дополнительно **14 Python-тестов** метрик и watchdog:
[лог](../../target/security-evaluation-se221/python-tests.log).
Независимый постпроцессор проверил фактические события и восстановление,
включая частичные журналы; [аудит](tables/independent-audit.json).

Сохранены и не скрываются неудачные подготовительные проверки. Первый запуск
тестов встретил отказ записи в системном Temp; повтор с явным `java.io.tmpdir`
в рабочем каталоге прошёл. Это не устанавливает источник прежних Windows-ошибок.
Третий предложенный DFS-оракул с expiry оказался слишком большим: исходный и
один сокращённый вариант достигли фиксированных 250000 узлов до завершения
эталона. Он удалён из ограниченного нового набора; бюджет не повышался,
INCOMPLETE эталона не принят за успех. Две завершённые нетривиальные задачи
и прежние lifecycle/expiry тесты прошли. Логи и объяснение в
[search-notes](search-notes.md) сохранены.

Изменение обхода подтверждено полными конечными оракулами и сохранением логики
отсечения/кэша, но два малых примера не являются формальной проверкой всех
возможных входов. Одна пара замеров не даёт статистического коэффициента
ускорения; старый поиск был цензурирован 30 s. Смешанная таблица старых и новых
запусков не является единым новым benchmark производительности. Модель
синтетическая, риск компрометации не добавлен в целевую функцию, бортовая
выполнимость и устойчивость ко всем правилам выбора не заявляются.

[Команды](README.txt), [протокол](protocol.md) и manifest позволяют проверить
сохранённые результаты без повторного запуска экспериментов. Новые архивы
содержат собственные исходники, JAR и доказательства; прежние результаты
остаются отдельными неизменяемыми входами с хешами.
