# SE2.5 — оставшийся спрос C1, только day2 SE2.4

Протокол до исполнения. Проверяем, даёт ли заблаговременная подготовка Multi
больше конфиденциально доставленных данных после раскрытия при неисчерпанном
спросе C1. Положительный результат не требуется.

## Входы и единственное изменение

Источник: target/security-evaluation-new-days/day2/models/{none,late-detected}.json.
Окно C1: 2026-10-12T00:08:37.296295166Z … 00:14:59.990386963Z,
382694091797 ns. PayloadProfile.frameDuration(): frameBytes × 10^9 / bytesPerSecond.
Кадр 1000 B / 100 B/s = 10000000000 ns. floor(duration/frame)=38;
B=1000×(38+1)=39000 B **в каждом направлении**. Даже 39 кадров одного
направления не помещаются в окно; совместная радиолиния не ослабляет эту гарантию.

Меняются ровно /scenario/contacts/0/payload/offeredUplinkBytes и
offeredDownlinkBytes: 1000 → 39000. Машинная рекурсивная проверка сравнивает
полные документы с точными decimal-числами. Исходные числовые токены сохраняются.
Имена сценариев и provenance остаются исходными (историческая строка LIGHT
описывает базу, не новый объём); новый режим однозначно задаёт configuration-audit.json.
Все окна, CP5400, пустые ключи, ограничения, minimum=1000 B/направление,
нагрузки C2/C3, кадры, скорости, затраты, атака p90 и notice+2 s неизменны.
Захватывается активная пара в момент атаки, без привязки к прежнему ID.

## Регистрация и исполнение

Используем точный SE2.4 JAR (commit 67870e66f043ce63f8370f1333b564184a6793c1,
SHA-256 2cefc98259eb910364db57105ad9e4265a4a4fbfa9f6d7efc77ecfee0039a4ee).
Текущий исходный commit 3621333; хеш новой обвязки и состояние дерева — registration.json.
Java-исходники не меняются, сборка и старые LIGHT-запуски не повторяются.
Восемь исторических day2 с их исходной регистрацией/версиями — отдельный контроль.

Ровно 8 новых попыток: none, затем late-detected; внутри CANONICAL, затем
CONTINUE_WAIT; внутри Next H=1, затем Multi H=2. Файлы моделей общие для обеих
политик и правил. SERVICE_FIRST, reuse ON, V2_EVENT_BOUNDARIES, пять критериев и
оба tie-break неизменны. 2M узлов/30 s поиск, 60 s контроллер, 90 s процесс,
-Xmx1024m, одна тяжёлая JVM. Нет повторов, дополнительных режимов или повышения лимитов.

Повторно используется неизменённая обвязка SE2.4 child/run/watchdog: до серии
проверка silent-child kill/reap при 2 s, elapsed <7 s. Обычный INCOMPLETE не
останавливает остальные случаи. Ошибка аудита/процесса или process>95 s /
controller>65 s прекращает серию с NOT_RUN для остальных. Пять секунд — допуск
диагностики записи/остановки, не увеличение бюджета поиска.

## Постобработка и трактовка

Прежние аудиторы независимо проверяют пять целей, security accounting, четыре
этапа восстановления и происхождение reuse. Из полного фактического журнала:

- Remaining UL/DL: offered C1 минус байты полных доставленных кадров C1 до
  события REVOCATION_RECEIVED_GROUND (порядок sequence разрешает равные времена).
  Частично переданные или прерванные кадры спрос не удовлетворяют.
- Confidential C1 after notice: сумма полных PAYLOAD_TRANSFERRED кадров C1,
  завершённых строго позже ground notice, чей направленный keyId не входит в
  фактически раскрытую пару. Это прежнее определение confidential delivery.
  Сохраняются времена, направления и sequence выбранных кадров.
- Independent frame in C1: первый допустимый независимый кадр по прежнему
  recovery-аудитору завершён в C1. Отсутствие — CENSORED на конце C1.
- Remaining C1 at activation/SA: C1.end − фактический момент соответствующего
  первого milestone; отрицательное значение явно означает событие после C1,
  не подменяется нулём. Отсутствующий milestone — CENSORED, значение null.

Для none реакция NOT-APPLICABLE. Для незавершённого исполнения финальные
метрики UNAVAILABLE; наблюдённый префикс сохраняется только как диагностика.
Сравниваются полные контроллеры, а не оценки отдельного горизонта. Предатаковая
установка и номинальные планы прослеживаются по full-trace. Меньшее раскрытие
может отражать меньший объём/иной момент передачи, само по себе не означает
более быстрое восстановление. Интервалы ожидания не суммируются при перекрытии.

## Владение и границы

Основной агент: регистрация → последовательные попытки → аудит → отчёт/архив.
Один короткий read-only проверяющий: только сопоставимость входов до запусков.
Никаких изменений solver/comparator/guard/controller. Старые файлы и архивы
контролируются сохранёнными хешами. Синтетические стоимости, конечный горизонт
и отсутствие вычислительных задержек в физической шкале сохраняются. Один
фрагмент и два правила не доказывают общую устойчивость преимущества.
