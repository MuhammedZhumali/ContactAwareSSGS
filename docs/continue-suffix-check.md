# Остаток оптимального плана после одного CONTINUE

Основа: `eab9671`, SE2.2.1. Проверен один номинальный кадр внутри того же контакта
при неизменном видимом горизонте. Производственные исходники, контроллер,
политики, comparator и прежние результаты не изменены. Подагенты не использовались.

## Условное обоснование

Пусть COMPLETE-план из наблюдения O имеет вид `[a] + q`, где `a` — завершённый
CONTINUE, а O′ — новое наблюдение после его фактического исполнения. Остаток q
сохраняет оптимальность **при выполнении всех условий**:

1. Фактическое состояние после кадра соответствует прогнозному дочернему
   состоянию. Сравниваются время, ключи/SA и дедлайны, счётчики, delivered bytes
   и направление следующего кадра, выполняемые операции, ресурсы, неопределённость,
   кадр в полёте, накопленные расходы и выданные ID. Одного SecurityState мало.
   Кадр действительно завершён; нет неожиданного события, атаки или отказа.
2. Не изменились текущий контакт, **весь** видимый прогноз (включая payload), H,
   `evaluationEnd`, ограничения, стоимости и модель моментов решений. Не открылись
   новые контакты. Дополнительные пробуждения и правила обработки событий совпадают.
3. Задача из O′ имеет то же множество допустимых продолжений и ту же семантику
   переходов, что исходное поддерево после a. Недостаточно совпадения кандидатов
   только на первом уровне. Генератор не зависит от старого корня или скрытого
   прошлого; при восстановлении сохраняются занятые ресурсы и начатая работа.
   `issuedKeyIds`, существующие/заблокированные ключи и `issuedOperationIds`
   сохраняются: `KeyGenerationIds.next` и `BranchEngine.nextOperationId` не должны
   заново выдавать использованные ID или менять идентификаторы плана.
4. Оценка относительно нового корня получается вычитанием одной и той же
   уже выполненной части для любого продолжения. Сохраняется прогресс текущего
   контакта: если кадр достиг порога обслуживания, контакт больше не приносит
   единицу в новой оценке. Useful time, CPU, bytes и created keys также считаются
   приращениями. Используется `accruedCosts`; повторно прибавлять `recordedCosts`
   нельзя. Нет нового терминального бонуса или другого изменения цели.
5. Полный порядок равенства неизменен: CONTINUE, WAIT, service; затем `until`
   и оставшийся канонический tuple, включая абсолютные времена, контексты,
   ключевые ID и контакт. Сохраняется также правило более короткого префикса.
   Порядок обхода к этому правилу не относится.

Для допустимого продолжения r тогда покомпонентно
`F_O([a] + r) = d + F_O′(r)`, где d — фиксированный выполненный вклад кадра.
Лексикографические пять критериев инвариантны к добавлению d. При равенстве
показателей удаление одинакового первого действия сохраняет сравнение полных
списков, включая случай собственного префикса. Если бы r обгонял q из O′,
`[a] + r` обгонял бы исходный COMPLETE-план — противоречие. Это условный аргумент
оптимальности; он **не доказывает**, что все условия автоматически соблюдаются
в любой точке производственного контроллера.

Проверенные места кода: `ExactHorizonPlanner.Search` фиксирует origin/evaluationEnd;
`SecurityPolicyController.executeAction` исполняет CONTINUE через общий симулятор;
`PlanningObservation.from` заново выбирает контакты и пробуждения;
`ContinuationEvaluator` вычитает исходный прогресс и accrued costs;
`PlanningResultComparator.comparePlans` сравнивает списки лексикографически.
`PlanningBranch.observation` не пополняет горизонт скрытыми контактами.

Сырые реальные и прогнозные snapshots не обязаны побайтово совпадать: различаются
журнал, режим и представление перенесённых итогов. Равенство всей проекции —
полезная проверка, но корректность восстановления будущей очереди и всех
допустимых переходов остаётся отдельным условием. `PlanningStateKey` предназначен
для одного фиксированного корня и не является готовым ключом межкорневого кэша.

## Один конечный пример и фактический результат

[ContinueSuffixOptimalityTest](../src/test/java/org/contactaware/security/simulation/ContinueSuffixOptimalityTest.java)
содержит один тест. Два контакта A: C1=[0,5), C2=[80,84), H=2. На контакт предложено
по одному UL/DL кадру по 100 B; кадр длится 1 s, оба необходимы для обслуживания.
Старая пара истекает в t=70, новая подготовлена заранее. INSTALL/SWITCH/OPEN стоят
по 1 s наземного CPU; PREPARE=100 s не помещается в горизонт. Это синтетический
профиль малого оракула SE2.2.1, не измерение оборудования и не серия X/Y/ISS.

Реальное исполнение подготавливает снимок: OPEN 0–1, UL 1–2. В корне t=2 есть
выбор INSTALL или CONTINUE. Полный DFS выбирает DL CONTINUE 2–3, затем INSTALL
3–4; в C2 выполняются SWITCH, OPEN и два кадра. Поиск с фиксированным первым
INSTALL тоже COMPLETE и имеет ту же пятёрку: это реальное равенство продолжений.

| Поиск / оценка | Статус | Узлы | Elapsed, s | Контакты; useful s; CPU s; bytes; новые ключи |
|---|---|---:|---:|---|
| Полный DFS из t=2 | COMPLETE | 15246 | 1.875 | 2; 3; 3; 0; 0 |
| Фиксированный первый INSTALL из t=2 | COMPLETE | 9487 | 0.719 | 2; 3; 3; 0; 0 |
| Новый полный DFS из t=3 | COMPLETE | 4663 | 0.365 | 1; 2; 3; 0; 0 |
| Уже выполненный CONTINUE 2–3 | — | — | — | 1; 1; 0; 0; 0 |

Исполнен только первый оптимальный шаг через существующий фактический executor,
новое наблюдение получено обычным `PlanningObservation.from`. Оно целиком совпало
с прогнозным. Новый DFS не получил старого плана, incumbent или memo. Его
**полный план равен оставшимся 11 действиям**, включая WAIT, времена и ID.
Обе номинальные версии остатка повторно исполнены: перед каждым действием
совпали полные наблюдения, кандидаты и следующие ключевые/операционные ID.
Терминальные оценки относительно обоих корней совпали с результатами DFS.

После DL текущий контакт уже обслужен: вычитаются один контакт и одна секунда,
но не предстоящие расходы INSTALL/SWITCH/OPEN. При начальном 1 s затрат OPEN
конечный накопленный CPU равен 4 s, продолжение стоит 3 s. Старый OPEN не
начислен повторно. Фактический журнал подтвердил ровно один новый доставленный
DL кадр и увеличение соответствующего счётчика SA.

## Отдельный ContinuationReuseGuard (2026-10-23)

Добавлены [ContinuationReuseGuard](../src/main/java/org/contactaware/security/simulation/ContinuationReuseGuard.java)
и [его тесты](../src/test/java/org/contactaware/security/simulation/ContinuationReuseGuardTest.java).
Контроллер, планировщик, comparator и целевая функция не изменены; guard пока
нигде не подключён к выбору действия. Он не хранит кэш, не запускает поиск,
не возвращает и не исполняет сохранённый остаток. Для проверки он номинально
воспроизводит **только первый CONTINUE** на отдельной ветви.

Результат — `Result(status, reason)` с `ALLOWED`, `REJECTED`, `UNSUPPORTED`.
API принимает `SearchEvidence(origin, result, rules, scope)`, новое фактическое
`PlanningObservation` и текущие `Rules(timing, tieBreak)`. Evidence должен быть
связан с исходным вызовом **неограниченного по первому действию**
`ExactHorizonPlanner.plan(origin)` в той же версии движка. Это обязательный
контракт доверенного вызывающего кода: сам `HorizonPlanResult` не сохраняет
origin, timing, tie-break и признак `planWithFirstAction`. Guard не может
восстановить или удостоверить эту связь по голому результату. Отсутствующая или
неизвестная provenance, результат фиксированного первого действия и архивный
результат без подтверждения той же реализации — `UNSUPPORTED`; статус
`INCOMPLETE` или `INFEASIBLE` — `REJECTED`. В тестах evidence создаётся прямо
рядом с вызовом `plan`, а не выводится из совпадения показателей.

Поддерживается один целый кадр внутри прежнего текущего контакта, V2-модель
моментов решений и неизменный полный comparator (CANONICAL или CONTINUE_WAIT).
В начале нет выполняемых операций, кадра в полёте, занятых ресурсов и
неопределённых контекстов. После кадра нет незавершённой работы. Контакты вместе
с payload, H, evaluationEnd, затраты и ограничения должны совпадать с исходными.
Сравнивается **весь record наблюдения**, с отдельными причинами для несовпадения
состояния ключей/SA/счётчиков, прогресса, accrued/recorded затрат, useful time,
числа созданных ключей, выданных ID, ресурсов, неопределённости и wakeups.

Почему этих условий достаточно в указанной области текущей реализации:

1. `BranchEngine` обрабатывает весь timestamp завершения кадра. Guard проверяет
   единственный доставленный кадр, его длительность и совпадение всего
   фактического наблюдения с обработанным прогнозом. Истечение старой пары в t=2
   допустимо; наблюдение с ещё активной старой парой после этого события отвергается.
2. Из исходного и нового наблюдений должны без потерь восстанавливаться их
   проекции. Дополнительно сравниваются конфигурации и будущие события прогнозного
   ребёнка и заново восстановленной ветви: время, kind, stable ID, reference ID,
   step index и deadline. Здесь допускаются только contact start/end и key deadline.
   Счётчик вставки может отличаться лишь при уникальности всех ключей порядка
   `(time, kind, stableId)`: в этой очереди он не разрешает равенств. Неизвестное
   событие, неоднозначность порядка или отличие очереди дают `UNSUPPORTED`.
3. Разница реестров уже зарегистрированных deadline разрешена только для
   необратимо выведенных из использования ключей. Их метаданные и выданные ID
   сохранены, повторная выдача ID запрещена. Все живые регистрации сохраняются.
   Это позволяет принять известное истечение, не предполагать исчезновение
   актуального таймера и не сравнивать сырые snapshots с разным представлением истории.
4. Генератор в этой версии зависит от наблюдения; V2 не добавляет иных таймеров.
   Переходы получают одинаковые ключи/счётчики, события, ресурсы и реестры ID.
   Поэтому по индукции одинаковые дальнейшие действия дают одинаковые события,
   ID, состояния и множества следующих действий. Новые операции/кадры получают
   уникальные ID, а deadline дедуплицируются; смещение счётчика вставки не меняет
   их порядок. При отсутствии незавершённой работы в проверяемой точке прошлый
   журнал влияет на будущее только через сохранённые итоги и состояние.
5. На том же видимом расписании оценка из нового корня вычитает общий выполненный
   вклад: обслуженные контакты, useful time, accrued CPU/bytes и created keys.
   Прогресс обслуживания сохранён, `recordedCosts` не прибавляется повторно.
   Оба имеющихся comparator сравнивают полные планы лексикографически; удаление
   одинакового первого действия сохраняет порядок, включая правило префикса.
   Применяется условный аргумент из начала заметки, а не равенство кандидатов
   первого уровня или `PlanningStateKey`.

Guard использует только наблюдения и их **номинальные** производные ветви.
Фактический `ExecutionSnapshot`, скрытые контакты, очередь атак и будущие исходы
операций не передаются. ALLOWED относится к оптимальности той же номинальной
задачи; он не удостоверяет отсутствие скрытых атак или будущих отказов и не даёт
