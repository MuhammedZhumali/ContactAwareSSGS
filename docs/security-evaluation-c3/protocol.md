# SE2.3 — влияние длительности C3 в X

Протокол записан до первого запуска серии. Владелец кода, сборки, JVM и анализа —
основной агент. Один подагент проводит только независимое чтение сопоставимости
входов. Статусы задач: входы подготовлены; review и сборка до регистрации;
затем 40 независимых попыток, аудит каждой, общая таблица/отчёт/архив.

Вопрос: сохраняются ли различия Next/Multi при изменении только конца последнего
контакта A в A → B → A? Точки C3: [80,83), [80,85), [80,89). Для 5 s используются
20 FINISHED из SE2.2.2 со своими исходниками, версиями и источниками. Для 3/9 s —
ровно 40 новых запусков ниже. Сетка не меняется после просмотра результатов.

## Неизменные входы и производные границы

Машинная сверка: configuration-audit.json. В 40 сценариях меняются только
`/end` и `/contacts/2/window/end`. Начало опыта t=-2, C1=[0,20), C2=[30,50),
C3.start=80; initialState, ограничения, costs, plan и disclosures неизменны.
Длительность опыта/плановый censorAt: t=83,85,89. Фактический observationEnd
частичной попытки указывается отдельно. Порядок JSON-множества authorizedContexts
нормализован, порядок остальных последовательностей не менялся.

Предложено в каждом направлении каждого контакта **9223372036854775807 B** —
прежнее явно заданное значение, оно не пересчитывается из длины окна. Кадр 100 B,
скорость 400 B/s, минимумы UL=DL=400 B. Реально доставляемый трафик ограничен
окном. Исходные параметры синтетические, аппаратной калибровки нет.

Атаки абсолютные: original=10, p70=14, p90=18, gap-midpoint=25. Уведомление НС
через 2 s после раскрытия. Модель захвата ключей и общая аварийная реакция прежние.
Различие между Next/Multi — только H=1/2; между правилами — CANONICAL/CONTINUE_WAIT.

## Расчёт до запусков

Кадр длится 0.25 s; для обслуживания нужны 8 полных кадров, то есть 2 s.
PREPARE=2 s, INSTALL=4 s, SWITCH=1 s, OPEN/REUSE=1 s; уведомление КА=0.4 s.
Для последовательного выполнения при свободных ресурсах и допустимом материале:

| Готовность на входе C3 | До первого кадра, s | До обслуживания, s |
| --- | ---: | ---: |
| Независимая пара уже активна, SA закрыта | 1.25 | 3 |
| Независимая пара установлена, ещё не активна | 2.25 | 4 |
| Пара только подготовлена | 6.25 | 8 |
| Материал ещё не создан | 8.25 | 10 |

Если предварительно требуется уведомить КА, к этим последовательностям добавляется
0.4 s. Локальная PREPARE может выполняться до C3; известные истечения, занятые
ресурсы и незавершённые операции могут менять доступность. Равенство времени
границе проверяется исполнителем. Это арифметическая проверка смысла 3/5/9 s,
не предсказание действий политики, не универсальный порог.

## Версия и бюджеты

Новая точка запуска SecurityEvaluationC3Main читает зафиксированный JSON.
Движок, guard, solver, comparator и policies не изменяются. Исходники фиксируются
локальным commit, собираются из git archive в отдельном source. Одна сборка,
один JAR для всех 40; manifest включает commit/tree, версии, хеши исходников/JAR.
Перед регистрацией — 23 целевых теста прежних guard/интеграции/полного остатка.
Полный набор 397 тестов заново не запускается: алгоритмы не меняются; его
результат SE2.2.2 остаётся историческим свидетельством.

Опции у всех новых попыток: SERVICE_FIRST, acceleratedServiceFirst(), reuse ON,
V2_EVENT_BOUNDARIES. 2 000 000 узлов и 30 s на поиск, 60 s контроллер включая
reuse и checkpoint, 90 s внешний watchdog, Xmx1024m, одна тяжёлая JVM.
Незавершённость не блокирует другие сочетания. Бюджеты не повышаются, автоматических
повторов нет. При техническом повторе нужна отдельная запись с исходной попыткой
и причиной. При нарушении корректности — сохранить пример и остановить серию.
Аудит фактического журнала и provenance выполняется после каждой попытки до
следующего процесса; неожиданные исключения требуют разбора.

## Метрики и сравнения

Используются audit_security_evaluation.py, recovery_metrics_se21.py и существующий
proof_audit из analyze_security_evaluation_se222.py с новым каталогом входов.
Пять целей: обслуженные контакты, useful time, CPU GS+SC, служебные UL+DL bytes,
созданные направленные ключи. Раскрытые до/после атаки байты и конфиденциальная
доставка — прежние определения. Четыре recovery milestones считаются от
REVOCATION_RECEIVED_GROUND: уведомление КА, допустимая независимая активная пара,
независимая SA, первый независимый кадр. Начальное состояние и интервалы готовности
сохраняются: первое событие не означает непрерывной готовности.

Нет события в FINISHED → CENSORED; нет применимого инцидента → not-applicable.
Для неполного исполнения все итоговые показатели → unavailable, наблюдённый
префикс хранится отдельно. Нули не подставляются. Средние задержки среди только
восстановившихся не вычисляются. originAt, плановый censorAt и observationEnd
отдельны. Время контроллера, SEARCH/SUFFIX_REUSE и узлы не смешиваются с CPU
security operations. Расчёт по-прежнему не продвигает физические часы контактов.

Все 60 сочетаний остаются в таблице. Для каждой длительности/атаки/правила —
попарные разницы Multi−Next, либо NOT_COMPARABLE при неполном результате. Вывод
объясняется состоянием на входе C3 и фактическими действиями. Три точки не
доказывают монотонность, универсальный порог или применимость к другим расписаниям.
Смешанные версии 5 s не образуют единый benchmark вычислительной производительности.
