# SE2.3 — длительность последнего контакта X

**При увеличении C3 с 5 до 9 секунд преимущество Multi исчезло при
CONTINUE_WAIT во всех пяти случаях: Next и Multi совпали по пяти целям,
конфиденциальной доставке, раскрытию до/после атаки и четырём этапам восстановления.**
Для 3 секунд сравнение не завершено: все Multi достигли лимита поиска. Для
9 секунд CANONICAL также не получены завершённые Multi. Следовательно, вывод
о равенстве при длинном окне подтверждён только для CONTINUE_WAIT.

Сетка не менялась: 40 новых сочетаний и 20 сохранённых FINISHED для C3=5 s.
[Полная таблица 60 строк](comparison.md), [CSV с версиями и origin/censor](comparison.csv),
[30 разностей Multi−Next](differences.md), [CSV разностей](differences.csv).

## Ответ по трём окнам

| C3 | Next, оба правила: обслуженные контакты для none / original / p70 / p90 / gap | Multi CANONICAL | Multi CONTINUE_WAIT |
| --- | --- | --- | --- |
| 3 s | 2 / 3 / 2 / 2 / 2 | 5 SEARCH_INCOMPLETE | 5 SEARCH_INCOMPLETE |
| 5 s, прежние результаты | 2 / 3 / 2 / 2 / 2 | 3 / 3 / 3 / 3 / 3 | 3 / 3 / 3 / 3 / 3 |
| 9 s | 3 / 3 / 3 / 3 / 3 | 5 SEARCH_INCOMPLETE | 3 / 3 / 3 / 3 / 3 |

Дополнительный обслуженный контакт Multi подтверждён в none и трёх поздних
атаках для 5 s при обоих правилах. В original при 5 s число контактов одинаково:
CANONICAL даёт Multi более быстрое восстановление и больше конфиденциальных
байтов, CONTINUE_WAIT — равенство с Next. Для 9 s/CW дополнительных контактов,
выигрышей в задержках или трафике нет. Для остальных новых пар результат
**NOT_COMPARABLE**, а не поражение Multi.

При 5 s у Multi наблюдаются независимая активация/SA/кадр после p70/p90/gap
при обоих правилах, у Next они CENSORED концом опыта. При 9 s Next восстанавливается
во всех атаках при обоих правилах; подтверждённые Multi/CW имеют те же задержки.
При 3 s Next восстанавливается только после original; остальные поздние атаки
у Next CENSORED, но данных для сравнения с Multi нет.

## Что происходит на входе C3

Неизменные 100 B/кадр и 400 B/s дают 0.25 s на кадр; обслуживание требует
400 B UL и 400 B DL, то есть 2 s передачи. OPEN=1 s, SWITCH=1 s, INSTALL=4 s,
PREPARE=2 s, уведомление КА=0.4 s. Эти суммы записаны **до запусков** в
[протоколе](protocol.md); они не предсказывают выбор политики.

После original у Next пара уже активна в t=19.4. В C3 достаточно OPEN 80…81 и
передачи 81…83: даже окно 3 s обслуживается. В none и поздних атаках такая
готовность отсутствует. В 3 s/p70 у Next есть лишь подготовленная пара; INSTALL
не помещается. В 5 s он может установить её, но не успевает завершить последующие
операции и независимую доставку. Подробные состояния и операции восстановлены
из фактов в [c3-entry-and-operations.json](../../target/security-evaluation-c3/c3-entry-and-operations.json).

В 9 s/none/CW обе политики выполняют PREPARE в 78…80, затем INSTALL 80…84,
SWITCH 84…85, OPEN 85…86. До конца окна остаются 3 s для передачи. В p70 пара
подготовлена раньше, но последовательность в C3 такая же. В p90/gap сначала
нужно уведомить КА: 80…80.4; OPEN завершается в 86.4, остаётся 2.6 s — минимум
обслуживания достигнут. Это фактическое объяснение, почему **9 s — проверенное
окно, при котором Next успевает обслужить C3 во всех пяти случаях**.

Длинное окно изменяет и более ранние решения Multi/CW. При 5 s ему нужна
заранее установленная пара; при 9 s достаточно подготовленной. Поэтому первый
независимый кадр Multi иногда появляется позже:

| Атака | Multi/CW, 5 s | Next = Multi/CW, 9 s |
| --- | ---: | ---: |
| original | 69.25 s | 69.25 s |
| p70 | 66.65 s | 70.25 s |
| p90 | 62.65 s | 66.65 s |
| gap | 55.65 s | 59.65 s |

Это задержки от уведомления НС, не от начала C3. Для p70 уведомление КА при
9 s, наоборот, быстрее: 0.4 s вместо 64.4 s при 5 s/Multi/CW. Активация,
открытие SA и доставка не смешиваются. В p90/Multi/CW раскрытые до/после атаки
байты меняются с 5900/100 (5 s) на 6800/800 (9 s), а конфиденциально доставленные
остаются 8600 B. Больше полезного времени не означает больше конфиденциальных байтов.

## Цена и границы результата

При 5 s дополнительный контакт в none стоит Multi +0.71 s CPU, +1080 служебных B,
+2 ключа и −1 s useful time относительно Next. В поздних атаках — +0.21…0.27 s
CPU, +280…360 B, без разницы числа созданных ключей; подробные знаки useful time
и трафика даны в разностях. При 9 s/CW все пять разностей равны нулю. Для
3 s и 9 s/CANONICAL цена Multi неизвестна из-за незавершённых поисков.

По завершённым данным устойчивость преимущества к обоим правилам остаётся
подтверждённой для прежнего окна 5 s. Расширить её на 3/9 s нельзя. Три точки
не определяют универсальный порог и не доказывают монотонность. Новые окна,
cryptoperiod, стоимости, Y/ISS и статья в этот этап не включались.

## Выполнение, аномалии и аудит

Из 40 новых сочетаний **25 FINISHED, 15 SEARCH_INCOMPLETE**. Вместе с прежними
20 — 45 FINISHED из 60 строк и 15 незавершённых. Все 15 обычных остановок имеют
TIME_LIMIT при t=0, когда Multi рассматривает C1/C2/C3; исследовано 193627…410421
узлов, до лимита 2M не дошли. Неисполненные incumbent-планы не приняты за результат.
Решатель не оптимизировался, эти попытки не повторялись.

Фактически было **43 новые попытки**: первоначальные 40 и три отдельно
зарегистрированных технических повтора. У трёх первоначальных CONTROLLER_TIME_LIMIT
elapsed процесса составил 343.344 / 561.078 / 46476.390 s при CPU потока около
2–3 s. В GC-журналах есть длинные промежутки между записями; это не измеренные
GC-паузы. Причина промежутков **не установлена**. Watchdog с настройкой 90 s
в этих случаях не обеспечил фактическую границу — строгая wall-time гарантия
не заявляется. Все три повтора с тем же JAR, входами и бюджетами завершились;
исходные файлы не заменены. [Все 43 попытки](attempts.csv),
[регистрация повторов](../../target/security-evaluation-c3/technical-repeat-registration.json),
[диагностика](../../target/security-evaluation-c3/timing-anomalies.json).

Независимые прежние постпроцессоры проверили 60 выбранных журналов и ещё три
исходные технические попытки — всего **63 журнала**, включая частичные. Для
всех новых попыток проверены **4057 связей reuse**, учёт затрат, счётчиков и
происхождение COMPLETE-корней. Итоговые метрики неполных запусков — unavailable;
плановый censorAt=83/85/89 и фактический observationEnd указаны отдельно.
Средних задержек только среди восстановившихся не вычислялось.

В изолированной Maven-сборке прошли **23 целевых теста**, без ошибок и пропусков.
Изменена только точка запуска серии; solver/контроллер/guard/цели неизменны.
Commit исполняемого кода `e3266427f33902e636e2eedb81c0b45fcc28bee3`, JAR SHA-256
`e7a97c56e6223c5ba2cb9408999f45d0d69ee3065ab63a014ef78ed289cf0fd3`.
Хешами проверена сохранность **2920 прежних файлов**. [Команды](README.md),
[валидация](validation.json), [manifest](artifact-manifest.json), [новый архив](c3-new-evidence.zip).
Смешанные версии 5 s и аномалии времени не позволяют считать эту таблицу единым
benchmark производительности; расчётное время по-прежнему не уменьшает контакты модели.
