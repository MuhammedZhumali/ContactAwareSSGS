## Почему хватает или не хватает окна

Автономный X: CP150, старый A активирован в t=-80, deadline=70; новая неактивная
пара живёт по maxMaterialAge=400. PREPARE создаёт материал за 2 s, INSTALL
подтверждает установку через 4 s; SWITCH и OPEN по 1 s. В C1/C3 одна линия A;
INSTALL нельзя выполнить в C2 со станцией B. Перенесённая пара остаётся допустимой
в t=80: CAN createdAt=3, material deadline=403; CW createdAt=15.75, deadline=415.75.
SWITCH в 81 начинает CP до 231. Дедлайны не перезапускаются от OPEN.

В X минимум — по 400 B при кадре 100 B/0.25 s: всего восемь полных кадров = 2 s.
При наличии INSTALLED наблюдённая последовательность SWITCH + OPEN + данные
занимает 4 s внутри C3=5 s, с запасом 1 s. Если INSTALL ещё нужен, последовательные
INSTALL + SWITCH + OPEN занимают 6 s до данных: даже если PREPARE уже выполнен,
эта цепочка в 5 s не помещается. В фактическом none Next её вообще не начинает:
при отсутствии улучшения первых целей лишняя подготовка увеличила бы расходы.
Это объяснение конкретных журналов и ограничений; полный минимум по произвольным
расписаниям/параллельным состояниям здесь не доказывается.

В X/9/CW после p90/gap первым идёт обязательное уведомление КА 80…80.4,
далее INSTALL до 84.4, SWITCH до 85.4, OPEN до 86.4. Восемь полных кадров
доставлены к 88.4 < 89. Для original пара уже активирована в 19.4 и допустима
до 169.4: в C3 достаточно OPEN и передачи, в том числе при C3=3 s.
Состояния ресурсов/подтверждения и отсутствие пересечений с radio-фазами
проверены прежним независимым аудитором всех журналов.

ISS LIGHT: кадр 1000 B/10 s, минимум по одному кадру UL/DL, всего 20 s.
Фактическая цепочка Next с PREPARED — 4+1+1+20=26 s; Multi с INSTALLED —
1+1+20=22 s. Окна возврата day1 405.994262695 s, day2 121.556396484 s:
обе цепочки помещаются, и сверх минимума здесь нет предложенных данных.
Порог X «8–10 s» к этим нагрузкам неприменим. При CAN подготовка g2 занимает
C1 AOS+5…7, установка +7…11, OPEN старого g1 заканчивается +12; Next открывает
g1 к +6. Все LIGHT-кадры C1 закончились до p90.

После p90 в ISS уведомление подтверждается за 0.4 s; CAN Multi переключается
на g2 к notice+1.4, Next создаёт/устанавливает/переключает её к +7.4.
Это **первая активация**, не непрерывная готовность: day2 g2 у Multi истекает
01:44:25.120977783, у Next 01:44:31.120977783; C3 начинается 01:47:18.202056885.
Day1 соответствующие expiry 04:42:14.374151611 / 04:42:20.374151611,
C3 04:44:40.713043213. В C3 доставляет уже g3. Multi заранее INSTALL g3 в C1,
Next делает INSTALL в C3. Первый кадр через 12/16 s от AOS — эффект готовности,
который существует и без атаки; он не означает дополнительных доставленных байтов.

## Точные строки для воспроизведения вывода

- X/5: `C3-5-X-{next,multi}-none-{canonical,continue_wait}`; ранняя атака —
  те же имена с `original-detected`, поздние — `p70-detected`, `p90-detected`, `gap-midpoint-detected`.
- X/9: `C3-9-X-{next,multi}-{none,p90-detected}-continue_wait`; все пять атак/контролей — в runs.csv.
- ISS: `day{1,2}-{next,multi}-{none,late-detected}-{canonical,continue_wait}`.
- SE2.5: префикс `demand-` перед именами day2; неисполненные incumbent не используются.
