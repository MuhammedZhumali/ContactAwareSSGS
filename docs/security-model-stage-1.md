# Этап 1: модель ключей и Security Associations

Реализован пакет `org.contactaware.security`: неизменяемые состояния, проверки ограничений и переходы жизненного цикла. Здесь нет симулятора, стоимости операций, алгоритма выбора, четырёх политик или результатов их сравнения. Контактные окна берутся из существующего `Model.ContactWindow`; импорт, выбор расписания и анализ gaps не меняются.

Это исследовательская модель управления метаданными. Она не генерирует секретные ключи, не шифрует кадры и не реализует протокол CCSDS SDLS. Корневые полномочия и защищённый механизм доставки ключей предполагаются доступными; их реализация находится вне этого этапа.

## Классы и границы ответственности

| Класс | Ответственность |
|---|---|
| `ContextId` | Идентичность пары КА–НС. |
| `Direction`, `KeyPairIds` | Разные направления и разные идентификаторы двух traffic keys; это не асимметричная криптографическая key pair. |
| `KeyState`, `KeyStatus`, `DeactivationReason` | Времена, статус, подтверждение установки, причина деактивации, прогресс nonce и история успешного использования ключа. |
| `SecurityAssociation`, `AssociationStatus` | Направленная SA, привязка ключа, поколение привязки, sequence number и признак синхронизации сторон. |
| `SecurityContext` | Две SA одной пары КА–НС и текущий открытый сеанс, если он есть. |
| `SecurityState` | Снимок всех контекстов и ключей одного КА, проверка согласованности ссылок и счётчиков. |
| `SecurityConstraints` | Общие ограничения времени и текущие известные разрешения/блокировки. |
| `SecurityConstraintChecker` | Проверка допустимости без изменения состояния; возвращает список причин отказа. |
| `LifecycleTransitions` | Применение допустимого завершённого шага и возврат нового снимка. |
| `SecurityAction`, `ScheduledSecurityAction` | Намерение будущей политики: действие, предполагаемое время начала, контекст, идентификаторы новых для контекста ключей и объяснение. |
| `SecurityChecks` | Внутренние проверки аргументов и структурных инвариантов. |

Конструкторы records проверяют структуру снимка. Для обычного изменения состояния следует использовать `LifecycleTransitions`; ручное создание снимков предназначено для доверенных исходных данных и тестов, а не для обхода истории переходов.

## Состояния и переходы

У каждого направления собственный ключ и SA. В первой версии две SA управляются совместно: их статусы совпадают, хотя счётчики и история использования ключей различаются. Контексты разных НС сохраняются независимо. В один момент допускается только один `OPERATIONAL` контекст КА.

Ключ: `PRE_ACTIVE → ACTIVE → DEACTIVATED → DESTROYED`. Неиспользованную подготовку также можно прекратить переходом `PRE_ACTIVE → DEACTIVATED`; возвращение к активному состоянию запрещено.

SA: `ABSENT → UNKEYED → KEYED → OPERATIONAL`. Остановка возвращает SA в `KEYED`; отвязка переводит `KEYED → UNKEYED`; удаление переводит `UNKEYED → ABSENT`.

| Метод `LifecycleTransitions` | Предусловие и результат |
|---|---|
| `createContext` | Авторизованная пара КА–НС, новый или `ABSENT` контекст → две `UNKEYED` SA. При восстановлении сохраняются идентичности SA. |
| `prepareKeys` | Существующий, не `ABSENT` контекст → два новых `PRE_ACTIVE` ключа. Подготовка локальная и не требует контакта; текущие привязки не меняются. |
| `confirmInstallation` | Живые `PRE_ACTIVE` ключи, совпадающий открытый по времени контакт и свободная для него радиолиния → подтверждённая установка на обеих сторонах. |
| `activateKeys` | Те же проверки плюс подтверждённая установка → `ACTIVE`, фиксируется время активации. |
| `bindKeys` | `UNKEYED` SA и допустимые активные ключи → `KEYED`; увеличивается поколение привязки, восстанавливается счётчик ключа. Это подтверждённая синхронизированная привязка. |
| `startContext` | `KEYED`, допустимый контакт и ключи, сохранённая синхронизация, допустимый gap для ранее использованных ключей → `OPERATIONAL`. |
| `recordProtectedTraffic` | Допустимый интервал внутри сеанса → увеличение счётчиков на явно переданное число подтверждённых защищённых кадров. |
| `stopContext` | `OPERATIONAL → KEYED`; ключи остаются активными, фиксируется успешное использование по направлениям. |
| `unbindKeys` | `KEYED → UNKEYED`; ключи остаются активными. Это семантика отвязки/Expire-SA, а не истечение срока ключа. |
| `deactivateKeys` | Ключи не привязаны к SA → `DEACTIVATED`. Причина `EXPIRED` требует достигнутого deadline; отмена подготовки требует `PRE_ACTIVE`. |
| `destroyKeys` | Только `DEACTIVATED → DESTROYED`. |
| `expireContext` | Локальное прекращение использования связанного контекста: `KEYED` или `OPERATIONAL → UNKEYED`, связанные ключи деактивируются. Независимые подготовленные ключи сохраняются. |
| `deleteContext` | Только `UNKEYED → ABSENT`. Удаление SA само по себе не уничтожает отвязанные ключи. |

Удалённые SA и уничтоженные ключи сохраняют метаданные в снимке. Идентификатор ключа повторно выдавать нельзя. `DESTROYED` обозначает состояние модели; фактическое стирание секретов на устройствах здесь не проверяется.

## Время и срок действия

Все времена передаются явно как `Instant`; системные часы не используются. `SecurityState.asOf` — время последнего применённого перехода. Переход назад во времени запрещён, несколько упорядоченных переходов в один момент разрешены. Проверка не меняет снимок и не запускает операцию.

Для ключа с временем подготовки `createdAt`, активации `activatedAt`, максимальным возрастом материала `A` и cryptoperiod `C`:

```text
до активации: deadline = createdAt + A
после активации: deadline = min(createdAt + A, activatedAt + C)
```

Сохранённый `notAfter` фиксируется при подготовке и может только уменьшиться при активации. Reuse, новое поколение SA, её удаление/восстановление и повторная привязка ключа не меняют его возраст. Проверка с более строгими текущими ограничениями может дополнительно сократить допустимость; смягчение конфигурации не продлевает исходно сохранённый `notAfter`. В будущем сравнении политики должны получать один и тот же фиксированный набор ограничений.

Контакт и интервал защищённой передачи считаются полуоткрытыми. Завершение онлайн-шага допускается при `contact.start <= completedAt < contact.end` и `completedAt < deadline`. Передача на `[from, until)` может завершиться ровно в `deadline` или `contact.end`, но не позже. Старт в deadline запрещён.

`stopContext` допускается ровно в конце контакта. Нельзя перенести снимок с открытым сеансом за конец его контактного окна: сначала нужно закрыть сеанс. На самой границе допускается снимок после последнего интервала трафика, чтобы следующим переходом выполнить остановку или истечение.

Статус не меняется автоматически с течением времени. Даже если в снимке остался `ACTIVE` ключ, checker запрещает его использование после deadline. Будущий симулятор должен своевременно вызывать переходы истечения; этот этап не содержит планировщика событий.

## Правила reuse

Проверки для старта/продолжения контекста включают:

- совпадение КА, НС и направления ключа; назначение этого типа ключей фиксировано — защита трафика;
- авторизацию контекста и отсутствие ключа в полученном списке блокировок;
- `ACTIVE`, подтверждённую установку, действующий deadline;
- `KEYED` SA, синхронизацию сторон и согласованность счётчиков;
- совпадение контактного окна, допустимое время и отсутствие другой открытой радиолинии;
- допустимый gap для каждого ранее успешно использованного ключа;
- запас счётчика без переполнения.

Для направления с предыдущим успешным использованием:

```text
gap = nextContact.start - key.lastSuccessfulContactEnd
0 <= gap <= maxReuseGap
```

Верхняя граница включена. Используется начало следующего окна, а не время завершения resume. Возраст и cryptoperiod проверяются отдельно на фактическое время операции/передачи. Допустимый gap сам по себе не разрешает reuse.

История обновляется при `stopContext` на фактическое время остановки только для направлений, где в этом сеансе зарегистрирован хотя бы один защищённый кадр. Пустой сеанс не обновляет историю. `canReuseContext` требует предыдущего успеха хотя бы в одном направлении; для первого старта применяется `canStartContext`. Если одно направление ещё ни разу не передавало кадры, у него нет recurrence gap, но все остальные ограничения действуют. Если оба уже использовались, gap проверяется для каждого.

В этой версии reuse между контактами отличается от возобновления прерванного сеанса: повторный старт тех же использованных ключей внутри того же окна после STOP даст отрицательный gap. Моделирование сбоев и восстановления внутри контакта относится к следующему исследовательскому расширению. Ротация на свежие ключи внутри контакта разрешена.

`blockedKeyIds` содержит только известные системе блокировки, например полученный отзыв или обнаруженную компрометацию. Скрытая атака не становится доступной политике автоматически. Модель атак здесь отсутствует.

## Счётчики и атомарность

`KeyState.nextNonceCounter` хранит прогресс использования материала независимо от SA. Привязанная SA зеркалирует его в `nextSequenceNumber`. Повторная привязка восстанавливает накопленное значение; ноль допускается для другого, свежего ключа. `generation` учитывает привязки, но не продлевает срок ключа.

Это абстрактный монотонный счётчик `long`, а не формат IV/nonce конкретного шифра или поля SDLS. При достижении предела счётчик не оборачивается. Генерация nonce, anti-replay window и обработка потерь кадров вне этого этапа.

Каждый метод возвращает новый неизменяемый снимок. Проверка обоих направлений предшествует фиксации результата: ошибка не оставляет один ключ активированным или одну SA переключённой. Ранее полученные снимки не меняются; внешние коллекции копируются.

## Что считается подтверждением и что добавит следующий этап

`confirmInstallation`, `activateKeys`, `bindKeys` и `startContext` принимают время уже завершённого подтверждённого шага. Подготовка подразумевает наличие материала у НС; `confirmInstallation` подтверждает установку на КА. Вызов метода является входным фактом модели, а не сетевым обменом или проверкой реальной подписи.

Создание/удаление SA и отвязка также отражают применённые изменения модели. Эти методы не утверждают, что удалённое изменение можно выполнить без связи или бесплатно. `expireContext` — локальный запрет дальнейшего использования, а не подтверждение удалённого стирания. Будущий общий исполнитель должен проверять маршрут, подтверждения, длительность и затраты каждого составного действия.

Имена намерений: `PREPARE`, `ESTABLISH`, `REUSE`, `ROTATE`, `STOP`, `EXPIRE_CONTEXT`. У `PREPARE`, `ESTABLISH`, `ROTATE` задаются идентификаторы целевых новых ключей. Для `ESTABLISH`/`ROTATE` материал может быть подготовлен заранее. Сам `ScheduledSecurityAction` ничего не исполняет. Составные действия будут собраны из переходов в следующем этапе; сейчас нельзя считать последовательные вызовы с одинаковым timestamp измерением нулевой стоимости.

## Конкретизация исходной модели для проверки

1. Две направленные SA управляются совместно; это явное ограничение первой версии. Если при `expireContext(EXPIRED)` истёк только один ключ, второй также выводится из использования с причиной `POLICY_RETIRED`.
2. История успешного использования ведётся по каждому ключу/направлению, а не только по последнему визиту станции. Поэтому давно не использовавшееся направление может потребовать ротации, даже если противоположное недавно передавало данные.
3. Deadline сохраняется в ключе, а прогресс nonce переживает отвязку и восстановление SA. Это закрепляет запрет продления жизни ключа и сброса счётчиков через reuse.
4. Для отменённой, отозванной или просроченной подготовки разрешён `PRE_ACTIVE → DEACTIVATED`; уничтожение остаётся отдельным терминальным шагом.
5. Для первого этапа успешное использование означает зарегистрированные подтверждённые защищённые кадры. Полезное время, объём данных, CPU, служебные байты и последствия компрометации ещё не вычисляются.
