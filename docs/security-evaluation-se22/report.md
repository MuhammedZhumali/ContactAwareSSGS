# SE2.2 — зависимость результатов от выбора равноценных планов

Ограниченный этап выполнен: **52 зарегистрированные попытки, 40 FINISHED,
5 SEARCH_INCOMPLETE и 7 PROCESS_ERROR**. Новые полные исполнения подтверждают,
что преимущества Multi в ISS CP5400 по восстановлению зависят от tie-break.
В шести случаях с завершёнными всеми четырьмя сочетаниями положительное
преимущество Multi, сохраняющееся при обоих правилах, **не обнаружено**.
Это результат данной небольшой серии, не доказательство отсутствия пользы
горизонта. Для поздних атак X сравнение двух правил осталось незавершённым.

## Что изменено и что проверено

Пять приоритетов неизменны: обслуженные контакты → полезное время → CPU КА+НС →
служебные байты → новые ключи. Только при полном равенстве применяется
лексикографический порядок планов:

* CANONICAL сохраняет прежний порядок действий и всех полей.
* CONTINUE_WAIT выбирает группу CONTINUE, затем WAIT, затем служебные операции;
  внутри — меньший `until`, затем прежний полный кортеж действия. Это явная
  версия stable sort Claude, включая порядок служебных действий между собой.

Выбранное правило проходит через итоговый comparator, сравнение suffix в memo,
представителей WAIT и отсечения по равной оптимистической оценке. Кэш локален
одному поиску; незавершённые поддеревья не выдаются за решённые. Порядок обхода
для обеих политик и правил сохранён прежним: изменение обхода не подменяет
изменение tie-break. Модель атак, фактическая реакция, ограничения, действия,
ресурсы и время контактов не изменены. Next H1 и Multi H2 внутри каждого правила
различаются только разрешённым горизонтом.

17 новых проверок сравнивают оба правила с полным DFS на малых примерах,
ускорения по отдельности и совместно, обратный обход, реально используемый memo,
доминирование каждого из пяти критериев, равные оптимальные первые действия,
сохранение корня/прогресса/частичных затрат и INCOMPLETE. Все входят в 361 тест.
Дополнительно прошли 14 Python-проверок метрик восстановления и watchdog.
Независимый учёт 45 экспортированных полных/частичных журналов прошёл;
**21 завершённый CANONICAL** совпал с SE2 по событиям и итоговым метрикам.

## Механизм X: оптимальные продолжения, а не список кандидатов

Перед решениями 3 и 12 сохранённого X-multi-none восстановлено фактическое
состояние исполнением записанных действий, без исторических поисков. Из одного
состояния получены H1/H2. Для каждого точного первого действия выполнен отдельный
поиск до исходного `evaluationEnd`, с тем же корнем учёта.

| Корень | H | Оптимальная пятёрка относительно корня | Все первые действия с этой оценкой |
|---|---:|---|---|
| t=1, перед PREPARE | 1 | 2; 38 s; 0.06 s; 80 B; 0 | CONTINUE |
| t=1, перед PREPARE | 2 | 3; 37 s; 0.77 s; 1160 B; 2 | PREPARE A; CONTINUE |
| t=3, перед INSTALL | 1 | 1; 36 s; 0.06 s; 80 B; 0 | CONTINUE |
| t=3, перед INSTALL | 2 | 2; 35 s; 0.57 s; 1160 B; 0 | INSTALL A; CONTINUE |

Все четыре множества полностью проверены CANONICAL: 7/11/7/11 точных кандидатов.
Они характеризуют одинаковую пятикомпонентную цель и допустимые продолжения,
независимо от того, какое правило выбирает победителя внутри множества.
Повторный поиск с CONTINUE_WAIT завершён для трёх корней; t=1/H2 остался
INCOMPLETE. Его incumbent совпадает по пятёрке с уже доказанным оптимумом,
но его канонический победитель по новому правилу не доказан. В таблицах этот
отдельный поиск и множество его проверенных альтернатив помечены неполными.

Пример t=3/H2 особенно нагляден: CANONICAL выбирает INSTALL в t=3,
CONTINUE_WAIT — передачу очередного кадра, а INSTALL в выбранном продолжении
откладывает до **t=15.75**. Оба завершённых продолжения дают
`(2, 35 s, 0.57 s, 1160 B, 0)`. Следовательно, запас установленного материала
к раннему обнаружению атаки — результат сочетания видимого C3 и выбранного
момента установки среди равных планов. H1 в этих же состояниях не выбирает
дополнительное обслуживание A для C3. Нельзя сравнивать пятёрки разных горизонтов
как итоговые результаты всего эксперимента; здесь они относятся к разным концам
оценивания. В t=3 текущий контакт уже обслужен, поэтому его повторно не считают.

Доказательства: [fixed-first-searches.csv](tables/fixed-first-searches.csv),
[optimal-first-action-sets.json](tables/optimal-first-action-sets.json);
полные планы, наблюдения, checkpoint и исходы в `target/security-evaluation-se22/probes/`.
Такие диагностики не запускались при каждом решении контроллера.

Оригинальные `TieProbe.java` и `TieBreakSensitivity.java` Claude не изменены.
Первый повторён для X/H2; второй вызван через прозрачный adapter для четырёх
X original сочетаний. Его полный контроллер воспроизвёл первый независимый кадр:

| Правило в программе Claude | Next | Multi |
|---|---:|---:|
| canonical | 69.25 s | 2.65 s |
| lazy | 69.25 s | 69.25 s |

Однако его проверка альтернатив использует канонические продолжения и допускает
ненулевую оценку незавершённого дочернего поиска. Поэтому эти воспроизведённые
значения — отдельное диагностическое свидетельство; они не заменяют новые
интегрированные запуски. Сопоставимый завершённый Multi canonical совпал также
по всем исполненным действиям. Новые Multi CONTINUE_WAIT X во всех пяти случаях
остановились по времени в t=0: завершённого сравнения полного X нет.

## Что показывают полные контроллеры

Время первого независимого кадра, секунды от уведомления НС:

| Случай | Next C | Multi C | Next A | Multi A |
|---|---:|---:|---:|---:|
| ISS CP5400 original | 27.4 | 18.4 | 18.4 | 18.4 |
| ISS CP5400 p30 | 5671.427337647 | 5667.427337647 | 5671.427337647 | 5671.427337647 |
| ISS CP7200 original | 27.4 | 27.4 | 18.4 | 18.4 |
| ISS CP7200 p30 | 5666.427337647 | 5666.427337647 | 5666.427337647 | 5666.427337647 |

C = CANONICAL, A = CONTINUE_WAIT. Для CP5400 original ранняя активация пары
равна **16.4 / 1.4 / 7.4 / 7.4 s** в том же порядке. Для p30 —
**7.4 / 1.4 / 7.4 / 7.4 s**. И выигрыш по активации, и 4-секундный выигрыш
по доставке p30 исчезли при альтернативном выборе. В original изменилось
также положение передачи кадра относительно уведомления: у канонического Next
КА уведомлён через 9.4 s, у остальных трёх — через 0.4 s.

При этом **все четыре итоговые пятёрки равны** в каждом из этих ISS случаев:
CP5400 original `(3, 60 s, 2.88 s, 4416 B, 8)`, p30
`(3, 60 s, 2.82 s, 4336 B, 8)`; CP7200 original
`(3, 60 s, 2.23 s, 3416 B, 6)`, p30 `(3, 60 s, 2.17 s, 3336 B, 6)`.
Равенство целевой пятёрки не означает равенства security-результатов.

Для CP5400 original раскрытые до/после компрометации байты и конфиденциально
доставленный трафик равны соответственно:

| Сочетание | Раскрыто до, B | Раскрыто после, B | Конфиденциально доставлено, B |
|---|---:|---:|---:|
| Next C | 900 | 1100 | 5000 |
| Multi C | 300 | 200 | 6000 |
| Next A | 500 | 200 | 6000 |
| Multi A | 500 | 200 | 6000 |

Разница Multi–Next здесь зависит от правила. Раскрытие относится к фактически
излучённым байтам, включая части прерванных кадров; конфиденциальная доставка —
к доставленным кадрам. Эти столбцы не образуют простую сумму всей доставки.
В CP7200 original оба горизонта переходят от 900/1100/5000 к 500/200/6000 при
смене правила: это эффект tie-break без различия горизонтов. CP5400 p30 и
CP7200 p30 дают одинаковые 2000/0/4000 во всех четырёх сочетаниях.

Контроли: Y без атаки равен во всех четырёх сочетаниях
`(3, 42 s, 0.18 s, 240 B, 0)`; CP5400 без атаки —
`(3, 60 s, 2.13 s, 3240 B, 6)`. Y original под альтернативой также одинаков
для Next/Multi; повтор Multi canonical потерян из-за I/O. CP7200 без атаки
не имеет завершённого Multi A. В X p90 и gap-midpoint CANONICAL даёт Multi
3 контакта против 2 у Next и на 1000 B больше конфиденциальной доставки;
для альтернативы устойчивость этих преимуществ **не проверена до конца**.

Все четыре этапа восстановления, статусы отсутствующих событий, периоды
допустимости и перекрывающиеся условия ожидания посчитаны тем же SE2.1 helper:
[milestones](tables/recovery-milestones.csv), [readiness](tables/readiness-intervals.csv),
[условия ожидания](tables/overlapping-conditions.csv). Никакого дополнительного
трафика не внесено. Первая активация не означает непрерывную готовность:
CP5400 g2 истекает до C3, поздний кадр использует другое поколение.
Отсутствие события не подменяется нулём. В Y после замены пары может вовсе не
быть нового контакта A; SA/кадр тогда цензурированы, хотя пара активирована.

## Бюджеты, расходы и незавершённые сравнения

До серии зафиксированы 2M узлов и 30 s на решение, 60 s на контроллер,
90 s внешний watchdog. Для диагностического корня — 120/150 s.
Бюджеты не повышались, попытки не повторялись. Одновременно работала одна
тяжёлая JVM. X checkpoint сохранён до ISS/Y. Времена описывают один локальный
запуск, не распределение производительности и не бортовой benchmark.

Для ISS CP5400 p30:

| Сочетание | Решений контроллера | Узлов | Сумма search elapsed, s | Search thread CPU, s |
|---|---:|---:|---:|---:|
| Next C | 47 | 1825 | 0.725 | 0.625 |
| Multi C | 46 | 168890 | 16.057 | 15.609 |
| Next A | 48 | 2508 | 0.936 | 0.922 |
| Multi A | 48 | 395760 | 36.414 | 35.359 |

Это CPU поиска; модельные CPU КА+НС из целевой пятёрки учитываются отдельно.
В сохранённых 3673 поисках: 3668 без причины остановки и 5 TIME_LIMIT.
У пяти Multi A X проблемное решение посещает 257386–264582 узла,
занимает около 30 s elapsed и 29.34–29.41 s CPU потока; GC delta 243–256 ms.
Bound занимает примерно 11.77–11.97 s, execution 5.35–5.54 s, generation
4.42–4.51 s, state key 4.43–4.62 s. Это измеренная вычислительная нагрузка
этих новых решений, не объяснение старого интервала 3361 s.
Максимальный recorded elapsed отдельного поиска — 30.0005115 s;
контроллеры честно остановились без итогового качества. Лимит узлов 2M
не достигнут: раньше сработало отдельное ограничение elapsed.

Семь PROCESS_ERROR вызваны `AccessDeniedException` в
`ExecutionCheckpointFiles.writeAtomic` при переименовании временного checkpoint.
Конкретная причина блокировки Windows не установлена. Это ошибка сохранения
свидетельств, не проигрыш политики и не SEARCH_INCOMPLETE. Последние checkpoint,
временные файлы и stack traces сохранены; полные затраты поиска этих процессов
недоступны. В серию не внесено исправлений I/O и скрытых повторов.
Точные случаи и времена snapshot — [failed-attempts.json](tables/failed-attempts.json).

[search-decisions.csv](tables/search-decisions.csv) содержит фазы, CPU, GC и
причины для каждого экспортированного поиска. GC MXBean отражает всю JVM;
его нельзя причинно приписать только одному методу. Перебор с другим полным
порядком существенно дороже в этих примерах; широкая оптимизация не выполнялась.
Поиск всё ещё не расходует модельное время контакта.

## Вывод для исследования

1. Воспроизведены равные оптимальные продолжения X и зависимость момента
   установки от tie-break; оригинальная программа Claude воспроизведена отдельно.
2. Новые полные ISS CP5400 показывают сочетание горизонта и правила: преимущество
   канонического Multi по восстановлению исчезает при CONTINUE_WAIT.
3. ISS CP7200 original показывает самостоятельный эффект правила у обоих
   горизонтов. Y none и CP5400 none сохраняют равенство.
4. Положительных преимуществ Multi, подтверждённых при **обоих** правилах
   завершёнными четырьмя контроллерами, эта серия не установила.
   Поздние X остаются кандидатами для проверки, с явно незавершёнными сравнениями.
5. Не следует описывать прежний ранний security-выигрыш как следствие одного
   горизонта. Целевая функция не минимизирует риск, а равные по ней планы
   имеют разную готовность к непредвиденному раскрытию ключа.

Следующий ограниченный шаг — отдельно исправить надёжность записи checkpoint
с воспроизводимым тестом отказа и новой версией, затем обосновать ускорение
поиска CONTINUE_WAIT без изменения его победителя. Повторы только конкретных
незавершённых сравнений потребуют новой регистрации; расширение до прежней
сетки и настройка цели ради преимущества Multi здесь не выполнялись.
Проверка двух правил не доказывает устойчивость ко всем правилам.
